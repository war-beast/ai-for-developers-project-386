# Агрегат «Запись» владеет инвариантом пересечения

Правило «записи не пересекаются, встык — можно» решал репозиторий (`TryAdd` в DAL), а запись в BLL была анемичной проекцией для API. Владение правилом переносим в домен: `Booking.TryCreate` сам применяет пересечение к существующим записям и конструирует запись (Id, `End = Start + длительность типа`, нормализация полей гостя); репозиторий сужается с `GetAll + TryAdd` до `GetOverlapping(start, end) + Add(booking)` — создание, выдача слотов и предстоящие встречи спрашивают у хранилища только конфликты нужного интервала. Между `GetOverlapping` и `Add` возникает гонка check-then-act, поэтому `Add` остаётся атомарным под блокировкой и возвращает `false` при пересечении — это guard хранилища, аналог exclusion-constraint в БД: решение об отклонении принимает агрегат, репозиторий лишь страхует целостность, и атомарность из ADR 0002 с тестом параллельных запросов сохраняется. `BookingInterval` остаётся в DAL: общий предикат для запроса репозитория и агрегата при зависимостях строго BLL → DAL.

## Consequences

- Валидация полей гостя остаётся в `BookingService`: отдельный «модуль валидации» из обзора архитектуры отклонён как спекулятивный.
- `GetUpcoming` читается как луч `GetOverlapping(сейчас, ∞)`, равнозначный `End > сейчас` и включающий идущую встречу.
- При переходе на настоящую БД guard `Add` заменяется constraint'ом (exclusion index), интерфейс репозитория не меняется.
